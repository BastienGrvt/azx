📏 Le standard pgx

Comment on définit un environnement de jeu « à la pgx » — et surtout pourquoi le standard a cette forme-là. De l'intuition jusqu'à l'implémentation d'un jeu complet.

1 Pourquoi ce standard existe (et pourquoi il est logique)

Imagine que tu codes un tic-tac-toe « normalement », en Python orienté objet. Tu écrirais quelque chose comme ça — et c'est parfaitement raisonnable :

❌ L'approche naturelle (OOP mutable)

class Jeu:
    def __init__(self):
        self.plateau = [0]*9  # état interne
        self.joueur  = 0

    def jouer(self, case):
        self.plateau[case] = ...  # MUTATION
        self.joueur = 1 - self.joueur

✅ L'approche pgx (fonctionnelle pure)

# l'état est une DONNÉE, à part
state = env.init(key)

# jouer = fabriquer un NOUVEL état
state2 = env.step(state, action)

# state n'a pas bougé. state2 est
# une nouvelle photo de la partie.

Pourquoi pgx rejette-t-il l'approche de gauche ? Parce que trois exigences, mises bout à bout, forcent la forme du standard. Suis la chaîne :

Le standard n'est pas un choix esthétique : c'est la seule forme compatible avec « des milliers de parties sur GPU via JAX ».
🎓 L'intuition physicienne

C'est exactement la structure d'une évolution dynamique : un vecteur d'état x et un propagateur x' = Φ(x, u). Personne n'écrirait un intégrateur où « l'atome se modifie lui-même » ; on écrit une fonction qui envoie un état sur le suivant. pgx dit la même chose pour les jeux : la partie n'est pas un objet qui vit, c'est une trajectoire d'états immuables reliés par une fonction de transition. Et comme pour un ensemble statistique, on empile B trajectoires indépendantes et on applique le même Φ à toutes (vmap).

Et la deuxième moitié du standard : l'interchangeabilité

La pureté ne suffit pas. pgx impose aussi que tous les jeux exposent exactement la même interface : mêmes champs dans le State, mêmes méthodes dans l'Env. Pourquoi ? Pour que le code d'IA soit agnostique au jeu : 

env = pgx.make("tic_tac_toe")   # ← change UNIQUEMENT cette ligne…
env = pgx.make("go_19x19")      # …et tout ton AlphaZero (MCTS, réseau,
env = pgx.make("chess")         #    self-play, entraînement) marche tel quel.
✅ Le standard en une phrase

Un environnement pgx = une structure de tableaux immuable (State) + trois fonctions pures (init, step, observe), avec des champs et des conventions identiques pour tous les jeux. La suite du guide détaille chaque morceau.

2 L'état est une photo, pas un organisme

Le changement mental n°1 quand on vient de l'OOP : un State pgx est une photographie complète et figée de la partie à un instant t. On ne « modifie » jamais une photo — on en prend une nouvelle.

La trajectoire d'une partie. step ne détruit rien : il produit la photo suivante.

Ce choix, imposé par JAX, a des bénéfices énormes qu'on récolte partout ensuite :

  • MCTS gratuit 🌳 — un arbre de recherche, c'est précisément « plusieurs futurs possibles depuis un même état ». Avec des états immuables, on peut garder state et générer 10 variantes step(state, a₁), step(state, a₂)… sans copie défensive, sans « annuler le coup » (le fameux undo_move() des moteurs d'échecs classiques, source infinie de bugs). C'est exactement ce que mctx fait avec le State dans embedding.
  • Parallélisme trivial — B photos s'empilent en une « pellicule » [B, …] et jax.vmap(env.step) avance les B parties d'un coup.
  • Reproductibilité — même état + même action = même résultat, toujours. Le hasard éventuel passe par une clé PRNG explicite.
ℹ️ « Mais recréer un état à chaque coup, c'est lent, non ? »

Non — c'est l'objection classique, et JAX la désamorce : sous jit, le compilateur XLA fusionne les opérations et réutilise les buffers quand l'ancien état n'est plus référencé (donated/aliased). L'immuabilité est une propriété du langage, pas du binaire compilé. Tu écris « pur », XLA exécute « en place ».

3 Le formulaire State : 6 champs publics, toujours les mêmes

Concrètement, un State pgx est un dataclass gelé (immuable). Le standard impose 6 champs publics, présents dans tous les jeux — c'est le contrat qui rend le code d'IA agnostique — plus tes champs privés à toi (préfixés _) pour la mécanique interne du jeu.

pgx.State — les 6 champs du contrat IDENTIQUES POUR TOUS LES JEUX
current_player À qui de jouer (id d'agent). C'est lui qui dit à ton AlphaZero quel « cerveau » doit choisir le coup.
observation Ce que voit le joueur au trait — le tenseur prêt à entrer dans le réseau (ex. tic-tac-toe : [3, 3, 2], un plan « mes pions », un plan « ses pions »).
rewards Le gain de chaque joueur à ce pas — un vecteur [num_players]. Jeu de plateau : [0, 0] partout, puis [+1, −1] au coup final.
terminated Partie terminée ? (victoire / nulle). Le signal pour discount = 0 côté MCTS et pour l'auto-reset côté self-play.
truncated Coupée pour une autre raison (limite de temps). Rare en jeu de plateau ; existe pour la compatibilité RL générale.
legal_action_mask Les coups permis — booléen [A]. Destiné au masquage des logits et à l'invalid_actions de mctx.
+ tes champs privés SPÉCIFIQUES À TON JEU
_x, _board, … Tout ce dont tes règles ont besoin (le plateau brut, le trait interne, un compteur de répétitions…). L'IA ne les regarde jamais : elle ne voit que les 6 champs publics. Contrainte unique : des tableaux JAX de forme fixe.
Le State a deux faces : la face publique, consommée par l'IA (réseau + MCTS), et la face privée, réservée aux règles.
⚠️ La contrainte cachée : formes fixes

Tous les champs doivent avoir une forme constante pendant toute la partie (pas de liste qui grandit !). Exemple typique : la liste des coups légaux n'est pas une liste de longueur variable, c'est un masque booléen de taille A fixe. C'est le prix du GPU : on paie en mémoire (tableaux pleins) ce qu'on gagne en parallélisme.

4 L'Env : tu écris les règles, pgx joue l'arbitre

Deuxième pièce du standard : la classe Env. Et ici, un point de design élégant que la doc ne met pas assez en avant : tu n'implémentes pas init/step/observe directement. Tu implémentes leurs versions privées _init/_step/_observe, et la classe de base les enrobe d'une couche d'arbitrage commune à tous les jeux.

Le pipeline de env.step. Tu écris l'étape 3 ; pgx garantit les étapes 1, 2, 4, 5 pour tous les jeux.

Ton travail se résume donc à 3 méthodes et 3 propriétés :

Ce que TU implémentes en héritant de pgx.core.Env LE CONTRAT CÔTÉ RÈGLES
_init(key) → le State de départ. La clé PRNG sert p.ex. à tirer qui commence.
_step(state, action, key) → le State suivant : appliquer le coup, mettre à jour legal_action_mask, terminated, rewards. Le cœur de tes règles.
_observe(state, player_id) → le tenseur d'observation du point de vue de player_id (canonique : « mes pions » d'abord, cf. §5).
id · version · num_players 3 propriétés d'identification : nom du jeu, version des règles (reproductibilité), nombre de joueurs.
✅ Pourquoi ce découpage est malin

Les invariants pénibles (« que faire si on step une partie finie ? », « et si l'action est illégale ? ») sont réglés une fois pour toutes dans la classe de base — et réglés d'une façon compatible GPU : pas d'exception levée (impossible sous jit !), mais des lax.cond qui gardent le flot de données uniforme. Le garde-fou n°1 est ce qui permet de vmap-er un batch où certaines parties sont finies et d'autres non : les finies « tournent à vide » sans corrompre quoi que ce soit.

5 Les trois subtilités qui font le standard

5a. current_player ≠ la couleur

La plus contre-intuitive. Dans pgx, il y a deux notions distinctes : la couleur (X ou O, noir ou blanc — une notion du jeu, souvent privée) et le current_player (l'id de l'agent : 0 ou 1 — une notion du tournoi). À l'init, pgx tire au hasard quelle couleur revient à quel agent.

L'id d'agent est stable à travers le batch ; la couleur est un détail interne du jeu. Indispensable pour l'évaluation par tournois.

5b. L'observation est canonique (« de mon point de vue »)

observation est toujours construite du point de vue du joueur au trait : le plan 0 = « mes pions », le plan 1 = « ses pions » — jamais « les X » et « les O » dans l'absolu. Conséquence directe pour ton AlphaZero : un seul réseau apprend pour les deux camps, et une même position vue par l'un ou l'autre donne des entrées cohérentes. (C'est le standard AlphaZero classique, pgx le grave dans le contrat.)

5c. Les récompenses : un vecteur, presque toujours nul

rewards a une case par agent, et en jeu de plateau il ne se passe rien avant la fin : [0, 0], [0, 0], …, [+1, −1]. Deux conventions à retenir :

  • Somme nulle pour les jeux compétitifs (victoire = +1 / −1, nulle = [0, 0]).
  • Après la fin (si on step quand même, cf. l'arbitre), rewards revient à zéro — pour ne pas compter deux fois la victoire dans un batch.
ℹ️ Où sont passés `done`, `info`, `env.reset()` de Gym ?

reset s'appelle init (et rend un State au lieu de muter l'env), done est éclaté en terminated/truncated (comme Gymnasium), et il n'y a pas de dict info : tout ce qui est utile est un champ typé du State. Si tu connais Gym, pgx = « Gym, purifié pour JAX, spécialisé jeux à N joueurs ».

6 Exemple complet : le tic-tac-toe, en deux couches

Voici comment pgx lui-même implémente le tic-tac-toe (code réel de ~/dev/libs/pgx, légèrement condensé). L'architecture est en deux couches, et c'est un pattern à copier pour tes propres jeux :

Séparer « les règles » de « la mise au standard » : la couche 1 reste simple, la couche 2 est presque mécanique.

Couche 1 — les règles pures (≈ 40 lignes)

class GameState(NamedTuple):
    color:  Array = jnp.int32(0)            # 0 = X, 1 = O  (la COULEUR au trait)
    board:  Array = -jnp.ones(9, jnp.int32)  # 9 cases : -1 vide, 0 = X, 1 = O
    winner: Array = jnp.int32(-1)           # -1 = personne (encore)

class Game:
    def step(self, state, action):
        board = state.board.at[action].set(state.color)     # poser le pion (version immuable !)
        idx = jnp.int32([[0,1,2],[3,4,5],[6,7,8],       # les 8 lignes gagnantes,
                         [0,3,6],[1,4,7],[2,5,8],       #   énumérées en dur : forme
                         [0,4,8],[2,4,6]])                #   fixe, zéro boucle Python
        won = (board[idx] == state.color).all(axis=1).any()  # victoire ? tout en tableaux
        return state._replace(board=board,
                              color=(state.color + 1) % 2,   # le trait change
                              winner=jax.lax.select(won, state.color, -1))

    def legal_action_mask(self, state): return state.board < 0   # cases vides
    def is_terminal(self, state): return (state.winner >= 0) | (state.board != -1).all()
    def rewards(self, state):           # [gain de X, gain de O] par COULEUR
        return jax.lax.select(state.winner >= 0,
                              jnp.float32([-1,-1]).at[state.winner].set(1),  # [+1,-1] ou [-1,+1]
                              jnp.zeros(2))                                 # nulle / en cours
⚠️ Trois réflexes JAX à repérer dans ce code
  • board.at[action].set(...) — la version immuable de board[action] = ... : elle rend un nouveau tableau.
  • jax.lax.select(cond, a, b) — le if/else compilable (les deux branches sont calculées ; pas grave, c'est minuscule et le GPU s'en moque).
  • La détection de victoire sans aucune boucle : les 8 alignements sont une matrice, la vérification un all/any vectorisé. Écrire des règles pgx = penser en tableaux, pas en for.

Couche 2 — l'adaptateur au standard (≈ 40 lignes aussi)

@dataclass
class State(core.State):                       # les 6 champs publics + le privé _x
    current_player:    Array = jnp.int32(0)
    observation:       Array = jnp.zeros((3,3,2), dtype=jnp.bool_)
    rewards:           Array = jnp.float32([0, 0])
    terminated:        Array = jnp.bool_(False)
    truncated:         Array = jnp.bool_(False)
    legal_action_mask: Array = jnp.ones(9, dtype=jnp.bool_)
    _x: GameState = GameState()                # ← toute la couche 1 vit ici

class TicTacToe(core.Env):
    def _init(self, key):
        current_player = jnp.int32(jax.random.bernoulli(key))  # pile ou face :
        return State(current_player=current_player, _x=Game().init())  # quel agent a les X ?

    def _step(self, state, action, key):
        state = state.replace(current_player=(state.current_player + 1) % 2,
                              _x=self._game.step(state._x, action))
        rewards = self._game.rewards(state._x)          # [gain X, gain O] par couleur…
        should_flip = state.current_player != state._x.color
        rewards = jax.lax.select(should_flip, jnp.flip(rewards), rewards)  # …retourné par AGENT ⭐
        return state.replace(
            legal_action_mask=self._game.legal_action_mask(state._x),
            terminated=self._game.is_terminal(state._x),
            rewards=jax.lax.select(terminated, rewards, jnp.zeros(2)))

    def _observe(self, state, player_id):     # observation CANONIQUE (§5b) :
        my_color = ...                          # la couleur de player_id
        return self._game.observe(state._x, my_color)  # plan 0 = « mes pions »

    # + les 3 propriétés d'identité :
    id = "tic_tac_toe";  version = "v0";  num_players = 2

Relis la ligne ⭐ : c'est la traduction couleur → agent du §5a en action. La couche 1 raisonne en couleurs (naturel pour les règles), la couche 2 remet tout dans le référentiel des agents (naturel pour le tournoi). C'est le travail typique de l'adaptateur.

✅ Bilan de l'exemple

Un environnement pgx complet = ~80 lignes : 40 de règles pures (pensées en tableaux) + 40 d'adaptateur quasi mécanique (les 6 champs, le flip des rewards, l'observation canonique). L'arbitre (chapitre 4), lui, est hérité gratuitement.

7 Valider et utiliser son environnement

Le test de conformité fourni par pgx

pgx livre un vérificateur du contrat : il joue des parties aléatoires et contrôle les invariants du standard (formes, mask jamais tout-faux avant la fin, rewards nuls hors terminal, etc.). Premier réflexe après avoir écrit un env : 

import pgx
env = MonJeu()
pgx.api_test(env, num=100)   # 100 parties aléatoires + vérification des invariants

Le triptyque d'utilisation (le « pourquoi » final du standard)

Si le contrat est respecté, ces trois lignes marchent — et c'est pour elles qu'on a tout fait :

init = jax.jit(jax.vmap(env.init))    # B parties initialisées d'un coup, compilé
step = jax.jit(jax.vmap(env.step))    # B coups joués d'un coup, sur GPU

states = init(jax.random.split(key, 1024))     # 1024 parties…
states = step(states, actions)                 # …avancent ensemble. C'était le but.
La promesse tenue du standard : la complexité « batch + GPU » n'apparaît jamais dans ton code de règles.

Bonus : la visualisation intégrée

state.save_svg("position.svg")   # dessine la position (tous les jeux pgx)
state                             # dans un notebook : s'affiche toute seule (_repr_html_)

Pour tes propres jeux, ce n'est pas obligatoire — mais implémenter un petit rendu (même ASCII) est le meilleur investissement debug que tu puisses faire.

8 Checklist : créer ton propre environnement

Encode l'état en tableaux de forme fixe. Le plateau, le trait, ce qu'il faut pour détecter la fin. Question-guide : « quelle est la photo minimale et complète de ma partie ? ». Pas de listes variables — des masques.
Écris la logique pure (couche 1) : init / step / legal_action_mask / is_terminal / rewards / observe sur ton GameState, en pensant tableaux (.at[].set, where, select — jamais de if ni de for sur des valeurs).
Teste la couche 1 seule. Quelques parties scriptées à la main (« X gagne en diagonale »), en Python normal — c'est encore facile ici, profite.
Écris l'adaptateur (couche 2) : le State avec les 6 champs publics + _x, l'Env avec _init/_step/_observe et les 3 propriétés. Points de vigilance : flip couleur→agent des rewards, observation canonique, rewards remis à zéro hors terminal.
Valide le contrat : pgx.api_test(env), puis le test ultime — jax.jit(jax.vmap(env.step)) sur un batch. Si ça compile et tourne, ton env est au standard.
Branche l'IA. Ton env parle maintenant la même langue que tous les jeux pgx : le recurrent_fn AlphaZero du guide V2 fonctionne dessus sans modification.
✅ Résumé du résumé

Le standard pgx découle de deux exigences : GPU (⇒ état = tableaux immuables, règles = fonctions pures, batch par vmap) et interchangeabilité (⇒ 6 champs publics et 3 méthodes, identiques pour tous les jeux, avec un arbitre commun hérité). Créer un env = écrire ses règles en tableaux, puis remplir l'adaptateur. Tout le reste — batch, jit, MCTS, self-play — vient gratuitement parce que le contrat est respecté.
