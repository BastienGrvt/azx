🔢 Comprendre le batch

Décoder les formes comme [B, A] dans mctx
[ B , A ]

L'idée en une phrase

✅ Le concept

Le batch, c'est le nombre de problèmes indépendants que l'on traite en même temps, empilés dans une dimension supplémentaire.
B = « combien de parties en parallèle », A = « combien d'actions par partie ».

Tu ne lances jamais une seule recherche MCTS. Tu en lances B d'un coup, côte à côte, qui n'ont rien à voir les unes avec les autres. La lettre B dans les formes est juste l'étiquette de cette pile.

🎓 Analogie physique

C'est exactement un ensemble de systèmes indépendants que tu fais évoluer en parallèle : au lieu de propager un vecteur d'état [A], tu empiles B répliques dans une matrice [B, A] et tu appliques la même opération à toutes en une fois. Aucune réplique n'échange d'information avec une autre — comme B trajectoires Monte-Carlo découplées. La dimension B est purement un axe de parallélisme.

Rappel express : une « forme » (shape)

Un tableau JAX/NumPy a une forme = la liste de ses tailles d'axes. Ça, tu le connais. Ce qui compte ici, c'est la sémantique de chaque axe : à quoi correspond chaque dimension.

FormeSe litExemple concret
[A]un vecteur de A nombresla politique sur A actions, pour une seule partie
[B]un nombre par partiela valeur estimée, une par partie
[B, A]B lignes, chaque ligne = A nombresla politique sur A actions, pour chacune des B parties
[B, ...]B copies d'une structure quelconqueB états de jeu empilés (le plateau, etc.)
ℹ️ La convention mctx

Dans mctx, le premier axe est TOUJOURS le batch. Dès que tu vois une forme, enlève mentalement le B du début : ce qui reste est « la vraie donnée pour une partie ».
[B, A] → oublie B → [A] = une politique. Simple.

✅ La lecture correcte

« prior_logits a la forme [B, A] » veut dire : pour chacune des B parties, un vecteur de A logits. La partie 0 croit à l'action 0 (logit 2.0), la partie 2 croit à l'action 3 (logit 3.1). Ce sont trois problèmes distincts résolus dans le même appel.

La règle d'or : les lignes ne se parlent jamais

C'est le point mental le plus important. Dans un tableau batché, la ligne i ne communique jamais avec la ligne j. mctx exécute B recherches MCTS totalement étanches : la partie 0 a son propre arbre, ses propres visites, son propre résultat. Le batch n'est pas un jeu à B joueurs — ce sont B univers parallèles.

Un appel muzero_policy sur un batch de 3 = 3 tuyaux étanches. Empilés, ils forment les axes B ; le GPU les traite d'un seul coup.
⚠️ Erreur mentale fréquente

B = 1 (comme dans main.py) ne veut pas dire « pas de batch » : la dimension existe toujours, elle a juste une taille de 1. C'est pour ça que la racine s'écrit jnp.array([[2.0, 0.0, 0.0, 0.0]]) avec deux crochets : le premier axe [B=1], le second [A=4]. Oublier ce crochet externe est l'erreur n°1 des débutants.

D'où sort la dimension B ? → vmap

Tu n'écris (presque) jamais la boucle sur le batch à la main. Tu écris ton code pour une partie, puis jax.vmap le « vectorise » automatiquement en ajoutant l'axe B devant. 

# Tu écris la logique pour UNE partie :
state = env.init(key)                 # une State,        formes sans B
state = env.step(state, action)       # une transition

# jax.vmap ajoute l'axe batch "gratuitement" :
keys   = jax.random.split(key, B)         # [B] clés
states = jax.vmap(env.init)(keys)          # [B] States empilés !
states = jax.vmap(env.step)(states, actions) # B transitions en parallèle
ℹ️ Le lien avec ta question sur pgx

Une State pgx est écrite pour une seule partie (pas de B). C'est jax.vmap(env.step) qui crée la dimension batch. D'où la phrase du guide : « la dimension B apparaît gratuitement ». mctx, lui, attend déjà des tableaux batchés en entrée — d'où les B partout dans ses formes.

Pourquoi s'embêter avec ça ?

Une seule raison, mais elle est décisive : le matériel.

  • Le GPU adore le parallélisme. Appliquer une opération à 1 vecteur ou à 1024 vecteurs empilés prend quasiment le même temps : le GPU fait les 1024 en simultané (SIMD). Traiter les parties une par une gâcherait 99 % de la puce.
  • AlphaZero a besoin de volume. L'entraînement demande des millions de positions. On génère donc 1024 (ou plus) parties de self-play en parallèle, d'un seul appel batché.
  • Une seule compilation. jit compile le graphe une fois ; changer B ne change pas la logique, juste la taille de l'axe.
🎓 En termes physiques

C'est de la vectorisation SIMD : « Single Instruction, Multiple Data ». La même instruction (une étape de MCTS) s'applique à un paquet de données (les B parties) simultanément. Exactement l'esprit d'un calcul d'ensemble où tu propages une pile de configurations sous le même opérateur, plutôt qu'une boucle Python lente sur chaque configuration.

Relecture du tableau mctx, maintenant que B est clair

Reprends les formes du guide principal — elles se lisent d'un coup d'œil :

ChampFormeTraduction « une partie + pile »
value[B]1 valeur par partie → une pile de B valeurs
prior_logits[B, A]1 vecteur de A logits par partie → pile de B vecteurs
action[B]1 action choisie par partie → pile de B entiers
action_weights[B, A]1 distribution sur A actions par partie
embedding[B, ...]1 état (de forme quelconque) par partie, empilé B fois
✅ Le réflexe à acquérir

Devant n'importe quelle forme mctx : (1) le premier axe est le batch, (2) masque-le mentalement, (3) lis ce qui reste comme « la donnée pour une partie ». C'est tout.
